# Redis + Horizon Queues and Docker Compose Deployment

Synchro runs slow or external work (emails, spreadsheet imports, and later PDF convocations, SMS/WhatsApp alerts, and iCal regeneration) as queued jobs on Redis, supervised by Laravel Horizon, and ships to production as a single Docker Compose stack built on FrankenPHP (Caddy with PHP built in): `app` (serves HTTP on `127.0.0.1:${APP_PORT}` and runs migrations on boot), `horizon` (queue workers), and `scheduler` (`schedule:work`), plus optional `mysql` (MySQL 8.0, per the cahier des charges), `redis` (queues, cache, sessions), and `phpmyadmin` services selected with Compose profiles, so any of them can be replaced by an external server. The host's nginx (Hestia templates in `docker/hestia/`) owns the domain and HTTPS and proxies to the app container. The `app`, `horizon`, and `scheduler` services share one image and one `storage` volume so workers can read files uploaded through the web tier.

Queued jobs stay thin: they call the same Single-Action classes as controllers (ADR 0009). Work is split across named queues with their own Horizon supervisors: `notifications` and `default` (short, retried with backoff) and `imports` (long, single attempt, because an atomic import must never be replayed after commit). Timeouts are ordered job < supervisor < `retry_after`. Side effects that must not escape a rolled-back transaction (such as invitation emails during a bulk import) are dispatched after commit. The Horizon dashboard is gated by the `monitor:queues` permission (ADR 0011), and the scheduler takes Horizon metric snapshots and prunes failed jobs, old import records, and stale invitation tokens.
